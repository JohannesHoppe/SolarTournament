# SolarTournament – developer introduction

SolarTournament is a space shooter in the browser: three.js, TypeScript, Vite, hosted as a static site. Short rounds (5 minutes), ships fight each other in an asteroid field. Multiplayer runs peer-to-peer without a game server.

The original from 2012 (CopperLicht, Node.js, Socket.IO) lives on the branch `old-main-2013` (and its farewell page on `old-gh-pages-2013`). It only serves as a source of assets and ideas and is never changed.

**Language:** everything in this repository is English: code, comments, docs, commit messages. Johannes and Claude talk German with each other; that does not change the language of the repo.

**Only what is, or what is meant to be:** code, comments, docs, the story, the TODO list and every text describe the game as it is now, or as it is planned, never as it was. No "no longer", "any more", "instead of the old", "now X", "changed to": a reader after a session (a later Claude, after its context was compacted, or anyone) knows nothing of the conversation in which something changed, and a sentence that leans on it makes no sense to them. Where something in the game itself changes within its story (Nicole's memory holding from chapter 2 on), say what holds from then on. History belongs in commit messages alone.

**The game in four languages:** English, German, Spanish, French (see `src/i18n/i18n.ts`). Every text the player sees is written in English where it is used and wrapped in `t('…')` (placeholders in braces, `t('Gate {n} of {total}', { n, total })`; whole phrases, never fragments put together); a text kept in a table and shown elsewhere is marked with `msg('…')` and shown through `t(value)`; a fixed text of a page carries `data-i18n` (attributes `data-i18n-attr`). The flight computer's and the announcer's lines in `src/music/lines.ts` are translated where they are spoken. Each new or changed text gets its translation in `src/i18n/de.ts`, `es.ts` and `fr.ts` in the same commit (keyed by the exact English text; `npm run i18n -- de` lists what is missing); the unit tests fail on a missing, stale or broken entry. Translations follow the catalogs' glossaries and voices (the Host addressed as du/tú/tu; the President's bombast, the announcer's cynicism, Nicole's flirt); names are never translated: people and peoples (the Rockborn), ships (Magpie, Patience, Lot 7731, the Sovereign), sponsors, products and the places' proper names (Psyche) read the same in every language, a pun on a name explained beside it; a place named by a plain word (the Boneyard, an arena's title) is translated; larger batches go to translators briefed on the universe.

**No "Newton" for players:** the word never appears in anything a player reads or hears (spoken lines, the story, the pages, the handbook, the about page, the README's opening and its universe): nobody cares about the old physicist, and "Newton is watching" is no line. Say what happens instead (a ship keeps its speed, it drifts on). Code comments and docs for developers may still call the flight model Newtonian.

**No foreign projects as references:** files and commit messages never name another project that served as a model or inspiration (for a license, a workflow, a pattern). Only what the repo actually uses is named: dependencies, assets and their licenses.

## Guideline: a universe of its own

SolarTournament has a universe of its own. We take inspiration from popular series, but only adopt two game principles:

- **A: Realistic physics as in The Expanse.** Reason: it simply was an awesome series. Whatever flies, collides, burns and breaks behaves the way it would out there, as long as it is fun: Newtonian flight, no sound in vacuum, no shields, lasers punch through. Where we deliberately deviate for the fun of it (e.g. the black hole of the Event Horizon, its pull far gentler than a real one of its size), the README says so explicitly.
- **B: Consciousness transfer into clones as in Altered Carbon, with one deliberate deviation.** Clones, printed by 3D printers, fly the ships; when a clone dies, the next one takes over. The ships are never printed: they are old fighters from the depots of centuries of war, used up in the Games, which is why none of them looks new (only the President's battleship is fresh from the dock). That explains the respawn. Mind the perspective in every text: the clone in the cockpit is the **pilot** (it flies, fights, feels the g-forces and dies); the one at the other end of the link who receives all of it, pays for the next clone and remembers every death is the **Host**. The player is addressed as the Host, never as "player". In the docs, "host" means only that: the announcer of Radio 2584 is the announcer, and the browser running an online round is the lead browser. Unlike Altered Carbon, where a stored memory is loaded into a new body (two bodies, two memories; the death itself is not remembered unless it is uploaded), the player, called the **Host**, is bound to the clones by a **live link**. The clone acts on its own, because radio links lag and only a mind in the cockpit reacts fast enough; but the link's bandwidth streams everything the clone lives through back into the Host's memory as it happens. When the clone dies, the Host holds all its memories and pain, the death included, and has to cope with it. The memory persists from clone to clone, dying hurts, and the soul rots a little more each time. This follows the reprinted expendable of the film Mickey 17.

On top of that, a look:

- **Beauty belongs to the elite; everything else is falling apart.** What the President, the Ministry and the rich own is beautiful and new (the battleship's polished armor, the Ballroom, the Sovereign's engraved gold). Everything else in the system is worn out, used up and neglected: stations, depots, haulers, racks and fighters are patched where they had to be (plates welded over holes, crooked and in other steel, cables run outside and left hanging), left broken where nobody needed them whole, rusted, sooted, painted over in whatever paint there was. Small impacts hit everything all the time; nobody comes to fix it properly. The solar system is coming apart because no one takes care of it, and every texture says so.

- **C: Neon and glitch, inspired by cyberpunk.** The future is screwed, and this is what it looks like: neon lettering, flickering tubes, sponsors everywhere, a picture that breaks up with every hit. Stylistic elements of well-known cyberpunk games may resonate, but without overdoing it; we have a style of our own, slightly retro (80s, old-school techno). Neon is a must.

We do not adopt names, terms or characters from the series and games; we fill the world with our own ideas.

### Music

Radio 2584 follows the maintainer's taste, written down in the README section "Radio 2584" ("Musical direction"): early techno, Kraftwerk, Daft Punk, hard beats, underground feeling, now and then German words with a rolling R. New musical decisions go there.

### Colors

Sun orange `#ff9d00` (hue 37°) for everything you press and everything that hits; its complement azure blue (217°) for information: `#0062ff` exactly as neon glow, `#4d91ff` lightened as readable text. Neon is a tinted white tube with layered `text-shadow`s in shades of the color (`--neon-orange`, `--neon-blue` in `style.css`); flickering respects `prefers-reduced-motion`. Use neon deliberately: the "Tournament" of the logo, plate headings, the sponsor sign, the radio title.

The HUD is the flight computer's projection and takes one color: azure (`--hud` and its shades in `style.css`), thin lines and letters with a soft glow and a dark hairline for readability, numbers in a fixed-width face. Orange in the HUD only for what the pilot has to act on now (a drive under the crosshair, a hit, a warning, the keys a drill asks for), red only for the ship in danger. What the flight computer draws into the world (the racing line, the flight school's markers, the reference plane's grid and the drop lines) is HUD too; the grid and the drop lines (and the orbit the readout sees) are an overlay drawn over everything, never hidden by rock, and kept faint, drawn after the black hole's lens (a scene of their own, `hudScene`), since the lens bends the picture of space, never the display; the world itself (gates, rocks, ships and their markers' tints) keeps its colors.

## Mandatory: every game principle is documented

Everything we come up with for the game must be documented, so that we can understand the SolarTournament universe thoroughly later: physics, damage model, rules, points, story, world.

- **README.md** explains the universe and the game physics for players and developers, with the actual numbers.
- Every change to a game rule or constant updates the README in the same commit. README and code must never drift apart.
- New story elements (time, world, characters, background) go into the README section "The universe".
- Constants in the code carry a comment with unit and reasoning.
- **The Pilot's Handbook** (`handbook.html`) tells the Hosts the rules they play by, with tactics, in all four languages. A change to a rule players use (controls, flight, weapons, items, a mode, an arena, points, the hangar) updates the handbook in the same commit, with its translations. Its numbers are placeholders filled from `src/handbook/numbers.ts`: from the game's constants where the page can import them, else from a number whose README wording the unit test finds; a digit written into a handbook text fails the test. Only what is built goes in; what the README says is coming stays out.

## Units

1 world unit = 5 cm. A ship is about 35 m long. Speeds in code in units/s, in the HUD in m/s (factor 0.05). 1 g = 196.2 units/s².

## Commands

```
npm install
npm run dev         # dev server on http://127.0.0.1:5173/
npm run typecheck
npm run dupes       # duplicated code (jscpd) and duplicated style rules (tools/dupes/css.ts)
npm test            # unit tests of the deterministic core (Vitest, in Node, about half a minute)
npm run e2e         # browser tests (Playwright: solo start, two tabs online); first once: npm run e2e:install
                    # DEV_PORT=5174 moves the dev server and the browser tests, so a second checkout (a worktree) tests beside the first
                    # the tests start their own dev server and stop if the port is taken; E2E_REUSE=1 tests against this checkout's server already running
npm run balance     # balance runs (Playwright, about forty minutes): every mode played out by bots in time-lapse in every arena
npm run soak        # the cheat checks in honest play (Playwright, about a quarter of an hour): three tabs, a round of every mode, nobody reported
npm run bench       # benchmark (Playwright, about ten minutes): the cost per frame of every feature, quality rung, arena and mode
                    # PROFILE=pixel8 as the reference phone (its screen, touch, its CPU speed); BENCH_SECONDS=<s> per measurement; BENCH_ONLY=quality for one section
npm run build       # static site in dist/ (renders the voice and checks the types first); the workflow CI runs duplicates and unit tests before a commit goes live
npm run check       # every quick quality gate in one run, summed up: types, duplicates, unit tests (tools/check/)
npm run check:full  # the same, then the browser tests and the balance runs
npm run sky         # packs the real sky's stars into public/assets/sky/stars.bin from the Yale Bright Star Catalogue (tools/sky/); only when the packing changes
npm run relays      # checks public Nostr relays and rewrites src/net/relays.json when the healthy ones changed (tools/relays/, weekly by a workflow)
```

## How to work

The same loop for every change, small or large. Follow it step by step; it holds everything that is easy to forget.

1. **Start.** `git pull`, then `npm run dev`. The dev server renders the voices first: quick from the cache, but many minutes after spoken lines changed. When only code changed and the voices are rendered, `node_modules/.bin/vite` starts the server at once.
2. **Fast loop while coding.**
   - `npm run typecheck` (a second) and `npm test` (a few seconds) after every step.
   - The dev server reloads the page by itself.
   - In the browser, `window.game` reads and sets the game's state (see Testing in the browser).
   - `game.log.summary()` sums up every death by its cause and the bots' decisions before it.
3. **Diagnose, never guess.** A balance run or a bug is explained from the dev log, a measurement or a test, never from a plausible story. What is not measured is called unknown.
   - **A change to how something is drawn is looked at.** A shader, a baked texture, a level of detail or a quality rung is checked on screenshots of what it changes, at the rungs it touches and drawn every way the game draws it (a mesh of its own, instanced, a billboard), before and after; a benchmark measures what a picture costs, never whether it is right. What it bakes gets a test that reads it back the way the GPU does.
4. **Texts.**
   - Every text the player sees or hears is written in English where it is used and wrapped in `t()`, `msg()` or `data-i18n`.
   - It gets its German, Spanish and French in the same commit; `npm run i18n -- de` (`es`, `fr`) lists what is missing, and the unit tests fail on a gap.
   - Spoken lines are cloned in Nicole's voice by the workflow Voice after the push; until then they fall back to Kokoro.
5. **Docs in the same commit.**
   - README: every rule with its numbers.
   - `handbook.html`: every rule players use, its tactics and numbers (see the Pilot's Handbook above), translated.
   - The folder's README: every file and what it does.
   - The structure table below.
   - `datenschutz.html`: every new data flow or storage key.
   - `TODO.md`: an idea Johannes names that is not built at once goes under "Ideas" the moment it is named, with the day; a roadmap item built gets its tick.
   - `docs/campaign/STORY.md`: the campaign's story follows the game as it is built; whatever a change builds or changes there (a line, a mission's numbers, a mechanic, a character) is written into the story in the same commit, the lines quoted as the game speaks them, so the story never describes an older game. What is not built yet stays sketched, and says so.
6. **Before every commit.**
   - `npm run check`: types, duplicates, unit tests, summed up in a table.
   - A change to the flight model, the flight computer, the input or the HUD's steering cues (the course marker, the crosshair, the racing line) has to pass the simulated Host's tests (`src/game/playability.test.ts`, `hostrace.test.ts`, `hostrace2.test.ts`, part of `npm test`): a human with ordinary hands must be able to fly the race and the flight school. Never loosen them to make a change pass; fix the change.
   - Commit with explicit paths (`git add <files>`, never `-A`), with an English message that says what the change does and why; no attribution lines.
7. **The full gates.**
   - `npm run check:full` runs everything above, plus the browser tests and the balance runs (about an hour).
   - Run it after every change to bots, weapons, damage, a mode's rules, the network or the round flow, and in any case every few merges. The game changes fast, and only the full run catches a rule that quietly breaks a mode, a race nobody finishes or two tabs that stop agreeing.
   - The balance runs leave the dev log of every round in `test-results/`, and a failure names the deaths by cause. `BALANCE_SLOW` gives them more time on a busy machine, `BALANCE_PAGES` plays fewer rounds side by side (see `e2e/README.md`).
   - A red gate is fixed before the next push, never ignored.
   - A code review (`/code-review`) runs at the effort level `medium` unless Johannes names another level.
8. **Push.** `git push origin main`, never to `stage_test` or `stage_prod` by hand: the workflow CI checks the commit (voices, types, duplicates, unit tests, the site's build) and moves it on to the stages only when all of it passes (see Hosting below).
   - Before it, `npm run build` must pass: the gates run the dev server, never the site's build, and a worker graph Vite cannot bundle (a worker that, through its imports, starts the one it is started from) passes every gate and fails only there.
   - After it, the push counts as live only once the workflow CI passed for the commit (`gh run list --workflow ci.yml --limit 1`) and the commit's check run "Cloudflare Pages" says success (`gh api repos/JohannesHoppe/SolarTournament/commits/<sha>/check-runs`), and both sites serve its build; a red CI moves nothing, and a failed Cloudflare build leaves the site on the last good one.
9. **Parallel work in worktrees.**
   - Every checkout runs its own dev server on its own port (`DEV_PORT=5174 npm run e2e`).
   - jscpd skips `.claude/worktrees` (ignored by git), so a worktree checks its duplicates on a copy outside it.
   - The dev server does not watch `.claude/`, so a worktree's edits never reload the main checkout's pages under a running test.
   - A worktree merges `main` before it reports.
   - Doc conflicts are resolved keeping both sides, one table row per line and one paragraph per bullet.
   - Benchmarks run one at a time on a quiet machine (1-minute load average below 3, no other browser busy), never beside another benchmark, test run or the code they are compared with; their numbers mean nothing otherwise. Every browser, tab and dev server a check opens is closed once it is done.
   - Many browsers at once on one machine slow each other down. The GPU-less test browser renders the title screen's pad and plays the audio in every tab, so a test that times out under load is rerun before it is called broken.

The Cloudflare account runs on the free plans only and the game spends no money: every service it uses (Pages, Functions, D1, TURN) stays within what is free, and where Cloudflare would bill beyond (TURN) the code keeps its own budget below that. Hosting is a classic Cloudflare Pages project (`wrangler.toml`), never Workers, built by Cloudflare (Git integration) from the two stage branches only, which the workflow CI (`.github/workflows/ci.yml`) moves to a commit of `main` once it passed its checks; Cloudflare's build takes the voice sprites CI rendered for the commit (`tools/voice/prebuilt.ts`) and runs only the types and Vite, far inside its time limit. Its server code is two Pages Functions of the same project. One is `functions/turn.ts` (`GET /turn`): it hands out short-lived TURN credentials and keeps the TURN key on the server; the key comes from the Pages project's environment variables `TURN_KEY_ID` and `TURN_KEY_API_TOKEN` (secret), set by Johannes in the Cloudflare dashboard for production and preview. Cloudflare has no spending cap for TURN, so the function keeps its own monthly budget (`MONTHLY_BUDGET_GB`): it reads the month's relay traffic through the GraphQL analytics with `CLOUDFLARE_ACCOUNT_ID` (a plain variable in `wrangler.toml`: with that file, Pages takes plain variables only from it, secrets still from the dashboard) and `TURN_ANALYTICS_TOKEN` (secret, Account Analytics Read) and hands out nothing when the budget is spent or the traffic cannot be read. The other is `functions/push.ts` (`/push`), the notification when a public tournament opens: its subscriptions in the D1 database bound as `PUSH_DB` (a `[[d1_databases]]` binding in `wrangler.toml`), its VAPID public key a plain variable there and the private one the secret `VAPID_PRIVATE_KEY`; without them it offers nothing, and it keeps to a daily budget of rows written (`DAILY_WRITES`). A third, `functions/admin.ts` (`/admin`), is Johannes' page of the game's figures behind Cloudflare Access: it checks the Access token itself against the team's keys (`ACCESS_TEAM` and `ACCESS_AUD`, plain variables in `wrangler.toml`) and answers 404 without them. Branches: work happens on `main`; `stage_test` is the test stage (https://test.solartournament.games), `stage_prod` is production (https://solartournament.games). Every page sends visitors of the raw Pages addresses (`solartournament.pages.dev`, `stage-test.solartournament.pages.dev`) on to these domains with a small inline script, keeping path and room code; the plugin `pageShell` in `vite.config.ts` writes it into every page (also into the static `public/404.html` in `dist/`), together with what else the pages share (icon, stylesheet, the seal behind the station pages, the head of the legal pages), and the build writes `dist/_headers` with the Content Security Policy (the inline script allowed by its hash; a new inline script, an external source or a new kind of connection needs the policy in `vite.config.ts` changed too). As long as the game has no real players yet, CI moves both stages (`PROMOTE_PROD` in `ci.yml`); once it has players, that is switched off and `stage_prod` only moves when Johannes asks for it.

Never use `npx`, always the scripts from `package.json`.

## Structure

The repository root is the Vite project: `index.html` (the game), `radio.html` (Radio 2584), `handbook.html` (the Pilot's Handbook, linked from the menu, the flight school's plate and the pause menu, which opens it at the section of the mode flown), `about.html` (what the game is, for those a search or a link brings, linked from the menu), `impressum.html` and `datenschutz.html` (German legal pages, linked from the menu and the radio page) are its pages, `public/` holds the static files, `tools/` the generators that write into `public/`, `docs/` the design documents of what is planned or being built (the solo campaign in `docs/campaign/`).

**Search engines.** The build writes each page a search can land on in every language at an address of its own, with its head, plus the sitemap (`tools/seo/`, checked by `src/seo.test.ts`). A title and a description are ordinary texts of their page; a new such page goes into `PAGES` in `tools/seo/pages.ts` and the build's inputs. `about.html` and the home page's description say what the game offers (arenas, modes, what it costs), so a change to that updates them in the same commit.

**The privacy policy follows the code.** `datenschutz.html` lists every data flow of the game: Cloudflare hosting, the fourteen localStorage entries, the radio page's last pressing in IndexedDB, the online tournament and its lobby (WebRTC between players, public Nostr relays, Cloudflare's STUN server and TURN relay, public tournament names, the cheat reports between the browsers), the notification when a public tournament opens (a subscription kept in Cloudflare D1 only once the Host switches it on, the lead browser's word that a public tournament is open, kept as a hash), the share menu (nothing sent until the Host picks a target; the networks it links to), the satire ads (no ad network), e-mail contact. Any change that adds a data flow (a new storage key, an external request, an ad network, analytics, another TURN or STUN server) updates the privacy policy in the same commit. Nothing is loaded from third-party servers at runtime.

**Every folder has a README** that says what the folder is for, what each file in it does and how it is used or run, short and for a human finding their way around. A new folder gets one, and a file added, removed or changed in what it does updates its folder's README in the same commit. The build leaves the READMEs in `public/` out of the site. One folder has none: `.github/`, whose README GitHub would show as the repository's front page instead of the root's; `.github/workflows/README.md` says what it holds.

`tools/relays/check.ts` (`npm run relays`) keeps `src/net/relays.json`: it takes the list's relays, Trystero's built-in ones and those the NIP-66 relay monitors report (kind 30166 on a few directory relays), checks each the way Trystero uses it (subscribe, publish a burst of three ephemeral events and read them back, three rounds) and keeps the 12 healthy ones, one per operator, those already in the list first, adding at most 2 a run that only the monitors name (their keys cost nothing). The workflow `.github/workflows/relays.yml` runs it every Monday and commits a changed list to `main`; it runs only our own code, with `contents: write` and the `GITHUB_TOKEN` alone. `tools/voice/render.ts` (`npm run voice`) renders into `public/assets/voice/` a sprite for the radio (every word and every sentence of the regime's lines in `src/music/lines.ts` with espeak-ng, English and German) and one for each language of the game (the announcer with espeak-ng in that language, and the flight computer's lines, Nicole: English with Kokoro, the other languages as her clone), translated through the catalogs. **Nicole's clone** (the whole pipeline in `tools/voice/README.md`): Chatterbox Multilingual V3 clones her from an English reference, line by line, checked by Whisper; `tools/voice/nicole.ts` pins what she is made of (Kokoro voice, reference, Chatterbox commit, model revision and the settings chosen by ear), `tools/voice/clone/` holds the tools, and the workflow `.github/workflows/voice.yml` clones whatever lines are missing and keeps them as assets of the release `voice-nicole` (never in the history); the build downloads them, and a line not cloned yet falls back to Kokoro reading espeak-ng's phonemes; a store that cannot be fetched (and has no copy in the cache) stops a build for the site (`CI` or `CF_PAGES` set), while on a developer's machine its lines fall back unstamped and uncached. The sprites are generated, not versioned (`.gitignore`): `npm run build` and `npm run dev` make them first, and only render them when the spoken lines or their translations, Nicole's clones, the tool (with the pinned Kokoro revision), the engines' versions (kokoro-js, phonemizer, transformers, onnxruntime, espeak-ng) or the ffmpeg binary's pinned SHA-256 changed. ffmpeg is a static build that `tools/voice/ffmpeg.ts` fetches from a fixed release only when the cache lacks it and uses only if its SHA-256 is the one pinned for the platform; a mismatch stops the build. Sprites (keyed by a hash of their inputs), the clones, ffmpeg and the Kokoro model (one folder per revision, used only once a download has completed) are kept in `_solartournament/` inside npm's cache directory (`~/.npm` by default): Cloudflare Pages keeps that directory between builds and no other, so a fresh checkout whose inputs did not change copies the sprite instead of rendering it (`VOICE_CACHE` moves the cache; where it cannot be written, the voice is rendered all the same). Never commit the sprite: generated binaries bloat the repository's history for good. The sprites the site goes out with are rendered by the workflow CI and kept in the release `voice-sprites` under their inputs' key, with a pointer per commit; Cloudflare's build takes them from there (`tools/voice/prebuilt.ts`) and renders only when they cannot be had.

### Typography

Typography matters. Running text is always justified, never ragged, with hyphenation on (`hyphens: auto`, the pages declare `lang`). Centered blocks are justified too and only center their last line (`text-align-last: center`). No line ends in a lonely word: text wraps with `text-wrap: pretty` (never `balance` on justified text: the shortened lines get stretched to full width again, with gaping spaces), and a short fixed text of a few sentences (the tagline) carries the class `sentences`, so it breaks between its sentences and is centered instead of justified. Headings and signs in Michroma, text in the system sans-serif.

### Supply chain

Every dependency is code that runs on Johannes' machine, in the build and in the players' browsers, so a new one is the exception and needs his yes.

- Prefer the platform and our own code: a share menu, a hash, a small helper are written here, not installed.
- No new package (npm, pip, a GitHub Action, a CDN script) without asking Johannes first, naming what it is for and why our own code will not do.
- Before proposing one, check it: who publishes it and since when, its weekly downloads and repository, recent ownership changes, install scripts (`preinstall`/`postinstall`), what it pulls in transitively, `npm audit` and `npm audit signatures`, and that the name is not a typo of a known package.

- Updates of existing dependencies are a change like any other: one at a time, with the same check, the changelog read, and `npm run check:full` green.

## Code rules

- **Determinism:** everything that concerns the shared world state (the arena of a round, its field, fragments, wreckage, the notes of Radio 2584) comes from seeded randomness (`Randomizer`), never from `Math.random()`. Otherwise peer-to-peer players see different worlds. `Math.random()` is only allowed for visuals (particles, flicker, glitches) and bot decisions.
- **Deterministic mathematics:** every mathematical function beyond `+ - * /` and `Math.sqrt` comes from `src/detmath.ts` (sin, cos, tan, asin, acos, atan, atan2, exp, expm1, log, log1p, log2, log10, pow, sinh, cosh, tanh, cbrt, hypot), never from `Math` and never through the `**` operator (a power is `pow` or a product), in all TypeScript, visuals and audio included; we never fall back to JavaScript's own. Reason, measured on GitHub's runners: `Math`'s transcendental functions differ in the last bits between x64 and ARM and between macOS and Linux (the Node version changes nothing), which bowed the racing line differently on x64; every browser computes the shared world itself, and the cheat checks compare what another browser reports with what this one computes, so all of them must get identical bits. The exact operations `Math.abs`, `floor`, `round`, `trunc`, `min`, `max`, `sign`, `fround`, `sqrt` stay. In `src/world`, `src/game`, `src/net` and `src/ship`, three.js's helpers that call `Math`'s trigonometry (`setFromAxisAngle`, `setFromEuler`, `slerp`, `angleTo`, `rotateTowards`, `applyAxisAngle`, `makeRotation*`, `rotateX/Y/Z`, an object's `rotation`, `MathUtils.damp`, the centripetal `CatmullRomCurve3`) are replaced by those of `src/detthree.ts`. `src/detmath.guard.test.ts` fails on any of them; `src/detmath.test.ts` holds every function within 1 ulp against a 192-bit reference and pins its bits; `src/determinism.test.ts` pins the bits of every arena's field, course, probes and a flown ship, and the workflow CI runs the unit tests on x64 and ARM Linux and on macOS. A function missing from the library is added there, with its tests, never taken from `Math`.
- **Human and alien ship are identical**, only their looks differ (shared hit radius); so is the Sovereign. Upgrades bought in the hangar change a ship for its own Host only, both interceptors alike, and online only up to their cap (see `game/hangar.ts`).
- **Bots obey the Hosts' rules.** A bot moves its ship only through a Host's controls (stick, drive, thrusters, trigger, and the actions a Host has, with their cooldowns), its clone takes the same strain, its clones wait as long, and it knows only what a Host's sensors show (line of sight, sensor ranges, storms, the lock warning). Only its decisions are its own (AI and skills). A new rule or ability applies to bots the same way; `src/ship/bots.test.ts` guards it.
- **The protocol has a version:** a change to a network message that a build before it would read otherwise (a key added, removed or required, a bound narrowed, a meaning changed) raises `PROTOCOL` in `net/transport.ts`, so the two builds never meet in a room.
- **No sound from outside:** in vacuum the player hears only what travels through the own hull, plus the flight computer's beeps, the radio and the link static in the headset. The one exception is a planet's air (Jupiter's, under its cloud deck, see `world/air.ts`): there sound carries, and the wind and thunder from outside are heard, through the hull like everything else.
- **Every object has a proper surface.** Nothing in the world is a plain colored material: every hull, module, wall, panel and prop carries a texture at its true scale (plates, seams, rivets, grime, wear), from `view/surfaces` (the world ship's ravaged plating, the depot paint, the industrial plating, hazard paint, solar cells, …) or a new surface drawn there. The universe is worn and used up; a station looks lived in and fought over, never clean grey. Only glows, light panels, neon and holograms are plain light.
- **Performance:** no objects created per frame in hot loops; reuse module-level scratch vectors.
- **Write nothing twice.** Code, markup and styles exist once: a repeated stretch becomes a function, a constant, a selector list or part of the page shell (`vite.config.ts`). `npm run dupes` checks it: jscpd (`.jscpd.json`: `src`, `tools`, `e2e`, `functions`, the four pages, `public/404.html` and `vite.config.ts`, from 5 lines and 50 tokens, threshold 0, files of any length) and `tools/dupes/css.ts`, which finds style rules with the same set of at least three declarations under different selectors. Run it regularly and at the latest before every commit; `npm run build` fails on a duplicate, so Cloudflare does not deploy one. A repetition that is technically unavoidable is marked with `jscpd:ignore-start` / `jscpd:ignore-end` (in a style sheet the comment `css-dupes: <reason>` before the rule) and one sentence why.

## Testing in the browser

In dev mode the game hangs on the window as `window.game`. It lets you read and set state (Playwright, `browser_evaluate`):

- Start a solo round: `game.playSolo('race', 'belt')` starts one of a mode in an arena (`null` for one by chance) at once, without the menu; the browser tests and balance runs start every round this way (`startSolo` in `e2e/game.ts`), and one test goes through the menu as a Host does (`startSoloByMenu`: `#start`, the mode's button, `#solo-launch`)
- Start a course of the flight school: `document.getElementById('school-racer').click()` (also `school-basic`, `school-gladiator`, `school-arsenal`, `school-tactician`); to start one at a drill, set `localStorage['solartournament.school-step']` to `{"arsenal": "probe"}` (the course and the drill's name, its key in `DRILL` in `game/school.ts`; "opening" and "closing" for a course's first and last words) before
- Simulate keys: `window.dispatchEvent(new KeyboardEvent('keydown', { code: 'KeyW' }))`
- Freeze time for screenshots: `game.timeScale = 0`
- Disable bots: set the other ships to `alive = false` and `respawnAt = Infinity`
- Multiplayer: open two tabs with `?local=1#t=<code>` (at least six letters or digits) and click "Join tournament" in both (BroadcastChannel, no internet); without `local=1` the same test runs over Trystero and real Nostr relays. Several tabs render too slowly without a GPU (frame gaps make browsers start over, see `CUT_OFF_MS`): switch rendering off with `game.composer.render = () => {}`. Cut a tab's link with `const t = game.online.session.transport; t._post = t.post; t.post = () => {}; t._recv = t.channel.onmessage; t.channel.onmessage = null` (restore both to reconnect); freeze it with a busy loop of a few seconds
- Render music offline: `const { renderPreview } = await import('/src/music/preview.ts')`, then `renderPreview('Orbit Terror', 'round', undefined, fromSecond, seconds)` (the title is the seed; a flavor can be forced); returns a WAV file as base64 that can be saved and listened to
- Read the development log (`src/devlog.ts`, only in development, cleared at every round's start): `game.log.summary()` counts the round's deaths by cause (rock, hull, gate, wreck, ram, knockout, laser, torpedo, nova, plume, flare, comet, shower, well, air, space, …), by ship, by what the victim was doing and by the decisions of victim and killer in the 3 seconds before, contacts between ships by outcome (bump, shove, ram) and shoves, the torpedoes launched and where they went off (on a ship, on a part, on the hull, on rock, burnt out; with a lost lock or a dead shooter), and in the President's Fleet the hits on the battleship by part and weapon, when each part broke and when it went critical; `game.log.filter('death')` (or `'decision'`, `'contact'`, `'shove'`, `'act'`, `'fleet'`, `'sync'` for what the lead's sync of the field set right here, or a function) lists the events, each death with position, speed, impact speed, killer and those decisions; `game.log.json()` is all of it. Every bot logs each change of its decision (race, attack, defend, flee, siege, probe, roam; avoiding rock, giving way to a ship) with its reason, and its acts (shove, hook, torpedo); every torpedo where it went off (`torpedo gone`). The balance runs attach each round's log to the result (`test-results/`) and put the deaths by cause into a failure's detail
- Record a flight (`src/recorder.ts`, only in development, cleared at every round's start): the last minute of the own ship, step by step, with the Host's controls, the mouse pointer, the commands the flight computer gave and the ship before each step. `game.recorder.download()` saves it as JSON (`download(10)` the last 10 seconds), `game.recorder.recording()` returns it; `replay()` in `src/test/cockpit.ts` flies it again through the autopilot in a unit test
- Trigger a glitch: `game.glitch.trigger(1, 5)`; idle glitches in the menu make element screenshots fail, so stop them with `game.nextIdleGlitch = Infinity`
- The picture's quality (`src/view/quality.ts`, README "Performance"): `game.graphics.rung` and `game.graphics.look` say what is drawn, `game.graphics.choose('low')` pins a tier (`'auto'` hands it back to the governor); the browser tests pin `low` in `localStorage['solartournament.quality']` before the page loads (`e2e/game.ts`). `?fps` shows the frame rate and the rung at the bottom of the screen; `?bench` (or `?bench=<seconds>`) runs the benchmark in the page, `npm run bench` in the test browser (`PROFILE=pixel8` as the reference phone)

The test browser renders without a GPU and composites the page without it (`--disable-gpu-compositing`, see `playwright.config.ts`); its frame rate says nothing about real hardware, the benchmark's table in it only compares costs with each other. Game feel and sound cannot be judged this way; Johannes tests those himself.
