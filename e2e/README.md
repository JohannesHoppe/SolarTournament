# e2e

Browser tests with Playwright, run against the dev server on port 5173 in Chromium with software WebGL (`playwright.config.ts`). First once: `npm run e2e:install`.

- `solo.spec.ts` (`npm run e2e`): a solo round of every mode and every course of the flight school start without errors; the hangar sells an upgrade and keeps it; two ships fly side by side through a gate at 100 m/s, and a dodge into the one at the rim knocks it into the housings, a kill for the kicker (without the dodge both pass).
- `online.spec.ts` (`npm run e2e`): two or three tabs of one tournament (`?local=1`) see the same world, a torpedo of one hits the other, they agree on Capture the Flag and the battleship, and they cast out a cheater.
- `layout.spec.ts` (`npm run e2e`): the HUD's pieces (round panel, alarms and message, transmission, radar, gauges, radio, kill feed, touch buttons), filled as full as they get, never cover each other, at 1280×720 and 800×360, with keyboard and with touch, in a race and in the flight school.
- `balance.spec.ts` (`npm run balance`, about ten minutes, not part of `npm run e2e`): every mode played out by bots in time-lapse; a bot of middling skill must hold its own, so a Host can too. Each round's development log (`src/devlog.ts`) goes with the result: its JSON in the test's folder under `test-results/` (`<mode>-<round>-<arena>.json`, attached to the report too), its summary in the annotations, and the deaths by cause in the detail of a failed check. Read a log with `node -e` or any JSON viewer: `summary.deaths`, `summary.afterDecision`, and the `death` events with the decisions before them say what killed the bots. On a busy machine the time-lapse plays slower: `BALANCE_SLOW=4 npm run balance` gives each check four times as long.
- `bench.spec.ts` (`npm run bench`, about ten minutes, not part of `npm run e2e`): the benchmark (`src/bench.ts`, README "Performance") in the test browser; `BENCH_SECONDS=<s>` per measurement (default 3), `PROFILE=pixel8` as the reference phone. The table goes to the console, the JSON and the table to the test's folder under `test-results/` (`bench.json`, `bench.txt`).
- `profiles.ts`: the devices the benchmark can pretend to be (`PROFILE=<name>`). `pixel8`: the Pixel 8 held sideways, 915 × 412 CSS pixels at a ratio of 2.625 (2400 × 1080 device pixels), touch, and its CPU speed in a browser.
- `game.ts`: shared helpers (open the game with the low quality tier pinned, launch a solo round, play a few seconds) and the game as it hangs on the window (`window.game`).

**The test browser.** Chromium draws WebGL in software (swiftshader) and composites the page without the GPU (`--disable-gpu-compositing` in `playwright.config.ts`): compositing the HUD's layers and the neon's glows in software GL held every tab to a few frames a second and slowed a second tab's start so much that the online tests timed out. The helpers also switch the scene's and the title screen's drawing off; the tests watch the game's state, not its picture.

**The Pixel 8 profile and its limits.** The screen and touch are the phone's. The CPU is slowed with `Emulation.setCPUThrottlingRate` to the phone's speed in Speedometer 2.0: the Pixel 8 makes 136 runs/min in Chrome 116 (Notebookcheck's review of the Pixel 8). The profile throttles by 4.5, a preliminary factor: it comes from Speedometer 2.0 runs in the test browser on the development machine (an Apple M4) while the machine was heavily loaded with other work, so its runs scattered widely and the factor is to be calibrated again on a quiet machine. To calibrate: run Speedometer 2.0 (browserbench.org) in the test browser at a few throttling rates and take the rate at which it scores 136 runs/min. The GPU cannot be slowed: swiftshader is a slow GPU of its own kind, so the frame times under the profile only compare features and rungs with each other at the phone's pixel count, where fill rate decides; the phone's own numbers come from `?bench` on the phone.

Run the browser tests before pushing changes to the network or the round's flow, and the balance runs after changes to bots, weapons, damage or a mode's rules. One deathmatch can turn any way, so a single red balance run can be chance: run it again before changing anything.
